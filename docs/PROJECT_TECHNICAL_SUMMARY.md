## 1. 数据版本管理：清洗不覆盖、可回溯

**问题**：清洗如果直接 `UPDATE/DELETE` 原表，用户改错无法恢复；图表、质量报告也会引用到「已经变了但没人知道」的数据。

**难点**：

- 每次清洗都要产生一份可独立查询的数据，同时不能让存储无限膨胀；
- 版本切换要同时更新列元数据、统计缓存、图表版本关联；
- 历史版本的规则需要能解释（规则后来可能被删改）。

**方案**：

1. 每个版本对应独立物理表 `data_<name>_<ts>_vN`，`dataset_version` 记录 `table_name / row_count / checksum / status / source`；
2. `dataset.current_version_id` 是唯一「当前版本」指针，切换版本只改指针，不覆盖数据；
3. 清洗规则在执行时写入 `dataset_version_rule` 快照（`rule_config` + `snapshot_hash`），删除规则不影响历史版本；
4. `JOBS_VERSION_KEEP`（默认 5）与 `JOBS_VERSION_MAX_AGE_DAYS`（默认 30）控制保留；
5. 恢复历史版本不是「回滚 SQL」，而是创建新的 `RESTORE` 任务并把目标版本切为当前，避免破坏已有版本链。

**效果**：R5 链路 A/C 验证通过——清洗生成 v2、恢复 v2 后 `currentVersionId` 正确指向 v2；删除/失败场景不会产生半成品版本。

## 2. 数据一致性：版本切换的原子性与缓存失效

**问题**：版本表写完但元数据没更新、统计缓存仍指向旧版本，会出现「数据是新的、列是旧的、统计是旧的」。

**难点**：MySQL 无外键，跨表一致性完全靠应用层；动态表 DDL 与业务表写入不在同一事务语义内。

**方案**：

- 版本从 `BUILDING` 开始，数据写入、行数、`checksum` 全部完成后才置 `ACTIVE` 并切换指针；
- 切换时统一刷新 `dataset_column`、清理 `stats_cache`；
- 关键写操作使用 `@Transactional(rollbackFor = Exception.class)`（导入、清洗建任务、版本、看板、导出记录等）；
- 失败路径把版本置 `FAILED`，当前指针不动，任务记录脱敏错误摘要；
- 恢复前用 `checksum`（行数 + 表校验和）比对目标表，避免恢复已被破坏的数据。

**效果**：R5「清洗失败不产生版本」验证：非法规则 404，版本数 1→1，`currentVersionId` 不变。

## 3. 图表 stale 与并发刷新：不静默套用新数据

**问题**：图表保存时绑定的是 v2，数据集后来清洗成 v3。直接拿 v3 重算会让用户以为看的是原口径；直接报错又会让图表不可用。

**难点**：

- 需要区分「用户没确认」「确认了但版本又变了」「字段被删了」三种情况；
- 两个并发刷新可能互相覆盖版本绑定；
- 检查版本与重绑之间仍可能产生新版本（TOCTOU）。

**方案**：

1. `saved_chart.dataset_version_id` 记录保存时版本；`stale = 绑定版本 != 当前版本`；
2. 刷新必须带 `X-Confirm-Version`；不带且 stale → 409「数据已更新，需要确认是否使用最新版本」；带的版本不是当前 → 409「数据版本已再次变化，请重新确认」；
3. 重绑使用**条件更新**（`WHERE dataset_version_id = 旧版本`），并发时只有一个成功；
4. 重绑后再次读取数据集当前版本，若又变化则**回滚本次绑定**并 409；
5. 字段缺失单独返回 409「字段已变更，请重新配置: ...」，不混同为版本冲突。

**效果**：R1 修复后「携带正确版本仍必然 409」的问题消除；R5 并发 generate 验证均 200/409，无 500，状态一致。

## 4. 异常语义：错误码、错误体与「不伪装成功」

**问题**：早期存在 409 被降级为 200、Blob 把 JSON 错误存成 CSV/PNG、看板单项失效导致整体 404 等「看起来成功/整体失败」的问题。

**方案**：

- `GlobalExceptionHandler` 统一映射：参数 400、认证 401、权限 403、资源 404、冲突 409、限流 429、不可用 503；响应体固定 `{code,message,data}`；
- `BusinessException` 携带业务码，禁止 Controller 捕获后返回 200；
- 前端导出按 `Content-Type` 判断：`application/json` 视为错误并提示，不落盘；
- 看板详情：单项图表/数据集缺失返回 `invalid=true` + 原因，看板仍 200；数据库/权限异常仍抛真实错误，不被「失效」吞掉；
- Nginx 429 使用 `error_page` + 命名 location 返回 JSON，而不是默认 HTML 错误页。

**效果**：R2 23 项、R5 异常用例全部通过；R4 实测 429 响应为 `application/json`。

## 5. 用户与数据隔离：私有 JWT 与公开匿名会话

**问题**：公开演示不能要求登录，但又不能让人看到别人的数据；同时要防止单 IP 刷爆资源。

**难点**：匿名会话没有账号体系，归属、配额、清理都要自建；Cookie 安全属性必须严格。

**方案**：

- 私有模式：JWT（`jjwt`），secret 必须环境变量提供；
- 公开模式：`POST /api/public/session` 创建匿名会话，token 以 SHA-256 存 `anon_session`；Cookie 为 `__Host-dc_anon` + Secure + HttpOnly + SameSite=Strict + Path=/；
- 所有资源带 `owner_type + anon_session_id`，`OwnershipService` 统一判定；不可见统一 404；
- 配额：数据集数、总存储、单文件、行数、列数、任务数、图表数、导出数、AI 调用/token；
- 清理：过期会话定时清理，`cleanup_item` 逐资源记录 `pending/done/failed`，`cleanup_log` 汇总。

**效果**：R5 链路 E 验证会话 B 访问 A 的数据集/列/导出/删除均 404，属主 200。

## 6. 持久化异步任务：可恢复、可取消、可重试

**问题**：大文件导入和清洗耗时长，HTTP 同步等待会超时；进程重启后内存任务丢失。

**方案**：

- `async_job` 持久化 `job_type/status/phase/progress/processed_rows/total_rows/retry_count/error_*`；
- `JobWorker` 轮询领取，心跳更新 `heartbeat_at`；超时无心跳的 `RUNNING` 视为可恢复；
- 取消写 `cancel_requested_at`，Worker 在批次边界检查并置 `CANCELLED`；
- 失败按 `max_retries` 重试，最终失败保留脱敏摘要；
- 导入超过阈值（默认 20000 行 / 5MB）自动转异步，接口立即返回 `jobId`。

**效果**：R5 任务中心、取消（最终 `CANCELLED`）、清洗期间并发导出均通过。

## 7. 文件解析与导出：流式、类型推断与编码

**问题**：大文件不能整表进内存；CSV 编码/BOM 会导致列名脏；Excel 日期/数字格式差异大；导出 CSV 需要 Excel 能正确识别中文。

**方案**：

- CSV 用 OpenCSV 逐行读取；XLSX 用 POI **SAX 事件模型**（`XSSFSheetXMLHandler`），不加载整本工作簿；
- 首行剥离 UTF-8 BOM，列名统一清洗、去重、空列名兜底；
- 前 200 行抽样推断 `INT/BIGINT/DECIMAL/DATETIME/VARCHAR/TEXT`，超长文本降级 `TEXT`；
- 按 `chunk-size`（默认 1000）批量插入，边写边更新进度；
- CSV 导出写 UTF-8 BOM，保证 Excel 打开中文不乱码；
- 旧版 `.xls` 明确拒绝并提示另存，避免 POI HSSF 的内存与格式问题。

**效果**：R3 BOM、非法日期问题修复并实测；R5 正常/损坏 XLSX 各 1 项通过。

## 8. 事务与并发控制：先保证正确，再谈扩展

**问题**：并发点击「执行清洗」可能建出两个任务；并发计算质量可能同时插入同一份报表触发唯一键冲突 500。

**难点**：这是典型 check-then-insert 竞态，单靠前端禁用按钮不可靠。

**方案**：

- `CleanService`：按 `dataset_id` 使用 `ConcurrentHashMap` 锁，把「活动任务检查 + 建任务」串行化，第二次返回 409；
- `DataQualityService`：按 `dataset_id` 加计算锁，避免重复插入 `data_quality_report`；
- 图表重绑使用条件 UPDATE，而不是「读-改-写」；
- 任务取消/重试使用状态条件更新，避免重复执行。

**效果**：R5 首测暴露的两个并发缺陷均已复现并修复；修复后复测「清洗 409/200」「质量 200/200」。

**边界（如实说明）**：两处锁都在 JVM 内，只对单实例有效。多实例部署需改为数据库唯一约束 + 乐观锁，或引入分布式锁（见 BACKLOG）。

## 9. 安全工程化：XSS、重复提交、确认机制

| 风险 | 方案 | 验证 |
|---|---|---|
| AI 内容 XSS | `marked` 渲染后经 DOMPurify 3.1.6 白名单净化；禁用 `style/form/input/iframe/object/embed` 与 `style` 属性 | 恶意载荷实测 `script/iframe/onerror/onclick/javascript:` 全部移除，`window.__xss` 未触发 |
| 重复提交 | 前端按钮 loading + 函数 guard；后端确认头、409、配额、条件更新兜底 | 重复清洗 200/409；导出无重复文件 |
| 破坏性操作 | DELETE 需 `X-Confirm: yes`；版本恢复 `confirm=true` 且异步执行 | R5 异常用例通过 |
| AI 密钥 | AES-256-GCM 加密，接口只返回掩码 | 代码路径审计 |
| 上传文件 | 临时目录不可静态访问，定期清理，公开模式强制扫描 | 配置与启动校验 |
| SQL 注入 | 动态表名/列名经 `SqlGuard` 白名单校验，值统一参数绑定 | 代码路径审计 |

## 10. 性能与可观测性

- **N+1 消除**：看板详情原先逐项查询图表/数据集/版本/列，改为每类一次批量查询 + 内存装配；实测 SQL 35 → 14，图表数增加时增量查询为 0。
- **缓存**：`stats_cache` 按数据集缓存统计结果，版本切换即失效；质量报表按 `dataset+version` 缓存。
- **指标**：Actuator + Prometheus，管理端口独立，Nginx 边缘不暴露。
- **审计**：`audit_log` 与 `ai_call_log` 分表，前者记操作，后者记 AI 调用成本与结果，均不含原始数据/凭据/Prompt。
